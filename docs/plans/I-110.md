# Plan I-110 — Plataforma de plugins comunitarios para engine, CLI e interacción UI

> **Issue:** [#110](https://github.com/phoson-lat/phoson-engine-minimal/issues/110) · **Prioridad:** P2 · **Esfuerzo:** L (5–8 días efectivos)  
> **Rama propuesta:** `feat/i110-community-plugin-platform`  
> **Estado:** Planificado — no se ha iniciado implementación.  
> **Objetivo:** que un paquete de terceros pueda instalarse, declararse, cargarse y extender Phoson mediante el único contrato `Plugin`: herramientas, middlewares, comandos slash, aspecto visual e interacciones declarativas con el usuario, sin modificar ni importar código interno de `phoson_cli`.

---

## 1. Contexto y problema

El sistema actual de plugins del engine es funcional y tiene un contrato canónico:

- `phoson_agent/plugin.py::Plugin` ofrece `configure()`, `initialize()`, `cleanup()`, `get_tools()` y `get_middlewares()`.
- `phoson_agent/plugin_loader.py::PluginRegistry` resuelve paquetes, paths, entry points (`phoson.plugins`) y loaders personalizados.
- `AgentEngine` carga los plugins, añade sus tools/middlewares y conserva las instancias en `_loaded_plugins`.

Sin embargo, el producto `phoson-cli` no expone esa extensibilidad de forma completa:

1. `phoson_cli/commands.py::COMMAND_SPECS` y sus derivados (`COMMANDS`, `_CMD_META`, `/help`, completer) son estáticos.
2. `phoson_cli/formatting.py::_TOOL_VERBS` es estático; una tool externa tiene fallback genérico y no puede aportar icono, verbo o detalle propio.
3. `phoson_cli/theme.py` solo conoce `dark`, `light`, `ansi` y `no-color`.
4. `PhosonConfig` no tiene `plugins`; `SessionController._rebuild_engine()` solo auto-construye MCP mediante `build_mcp_plugins()`.
5. El one-shot (`phoson_cli/__main__.py::_run_oneshot`) también solo recibe MCP, por lo que no hay paridad entre el CLI interactivo y scripting.
6. No existe una utilidad de instalación/gestión de paquetes de plugins para usuarios de la comunidad.
7. Un plugin no puede pedir confirmación, solicitar datos estructurados ni publicar un TODO/progreso/panel en ambos frontends sin depender de los internals de Rich o prompt_toolkit.

La consecuencia es que crear un plugin de comunidad con UX propia exige un fork o cambios directos bajo `phoson_cli`, lo cual contradice el objetivo de un sistema de plugins reutilizable.

---

## 2. Objetivos, no objetivos y principios

### Objetivos

- Mantener **un solo contrato `Plugin`**; no introducir `PhosonPlugin`, `CliPlugin` ni un segundo loader.
- Soportar plugins instalados desde PyPI y repositorios Git/GitHub, con origen y versión/commit trazables.
- Exponer comandos, render de tools, temas e interacción de UI desde el mismo `Plugin` que ya declara tools/middlewares.
- Mantener paridad funcional entre fullscreen, REPL clásico y one-shot/CI mediante degradación explícita.
- Conservar compatibilidad con `phoson_plugin_mcp`, `phoson_plugin_checkpoint` y `phoson_plugin_memory` sin editarlos.
- Evitar que `phoson_agent` dependa de Rich, prompt_toolkit o cualquier módulo `phoson_cli`.
- Hacer los contratos de extensión públicos, tipados, pequeños, declarativos, documentados y cubiertos por tests.

### No objetivos de esta entrega

- Ejecutar plugins Python en un sandbox real. Un plugin instalado se ejecuta con permisos del usuario; el instalador debe declararlo claramente.
- Construir un marketplace/registro central, reputación, firma criptográfica o resolución de dependencias entre plugins.
- Permitir widgets arbitrarios, HTML/JavaScript, callbacks de prompt_toolkit/Rich u objetos de layout dentro de plugins.
- Permitir que un plugin mutile directamente `ConversationTree`, el layout de fullscreen o la configuración global sin una API explícita.
- Actualizar plugins automáticamente sin consentimiento del usuario.

### Principios de diseño

1. **Datos, no widgets.** El plugin devuelve dataclasses/estructuras neutrales; cada frontend decide cómo renderizarlas.
2. **Paridad con degradación segura.** Toda interacción se representa en fullscreen y clásico; one-shot no lee stdin inesperadamente y responde `unavailable` o `cancelled`.
3. **Estado por sesión, no global.** Catálogos de comandos, specs visuales y extensiones de tema se construyen por `SessionController`; no se filtran entre controladores, rebuilds o tests.
4. **Core reservado.** Los comandos nativos ganan siempre y no son sobrescribibles.
5. **Instalación reproducible.** Un source mutable se resuelve y registra a una versión/tag/commit concreto.
6. **Una instancia, todos los hooks.** El mismo objeto de plugin ya inicializado atiende tools, middlewares, comandos, render specs, temas y UI; no se carga una segunda instancia para el CLI.

## 3. Diseño propuesto

### 3.1 Módulo de contratos neutral: `phoson_agent/cli_extensions.py`

Crear un módulo público que contiene contratos de datos y protocolos sin dependencias de UI. `phoson_agent` continúa siendo independiente de `phoson_cli`.

#### Comandos

```python
@dataclass(frozen=True)
class CliCommandSpec:
    """Un comando slash contribuido por un Plugin."""

    names: tuple[str, ...]              # incluye '/', primer valor canónico
    help: str                           # una línea
    handler: str                        # nombre de método async en el Plugin
    category: str = "Plugins"


@dataclass(frozen=True)
class CliCommandInvocation:
    name: str
    args: str
```

El handler se resuelve sobre la instancia cargada del plugin, en vez de guardar una función en el spec. Así los specs permanecen serializables/descriptivos y no exponen clases del CLI:

```python
class DeployPlugin(Plugin):
    def get_commands(self) -> list[CliCommandSpec]:
        return [
            CliCommandSpec(
                names=("/deploy-status",),
                help="Show deployment-plugin status",
                handler="handle_deploy_status",
                category="Deployment",
            )
        ]

    async def handle_deploy_status(
        self,
        command: CliCommandInvocation,
        context: CliCommandContext,
    ) -> bool:
        context.notify("info", "No deployment is running.")
        return True
```

`True` mantiene el REPL abierto; `False` solicita salir. Un comando de terceros no puede usar nombres reservados para cerrar/reemplazar comandos core, pero se conserva el retorno por consistencia del dispatcher.

#### Render de tools

```python
@dataclass(frozen=True)
class ToolRenderSpec:
    tool_name: str
    verb: str
    icon: str = "⚙"
    detail_handler: str | None = None
    result_handler: str | None = None
```

Los handlers opcionales reciben datos simples (`tool_name`, `args`, `result`, `error`, `duration_ms`) y devuelven bloques neutrales, no `rich.Text`, `Panel`, `Float` ni callbacks UI. En v1, `verb` e `icon` son obligatorios para el ejemplo; los handlers especializados se implementan solo si el contrato de bloques ya está listo.

#### Temas

```python
@dataclass(frozen=True)
class ThemeExtension:
    name: str
    description: str
    base: Literal["dark", "light", "ansi", "no-color"] = "dark"
    tokens: Mapping[str, str] = field(default_factory=dict)
    extra_tokens: Mapping[str, str] = field(default_factory=dict)
```

- `tokens` solo puede sobrescribir los tokens conocidos del tema base.
- `extra_tokens` es para renderers del propio plugin y nunca será requerido por renderers core.
- `name` es único, case-insensitive, y no puede reemplazar los cuatro nombres built-in.
- La extensión se convierte dentro de `phoson_cli/theme.py` en un `Theme` inmutable completo derivado de su base.

#### Bloques UI declarativos

Definir una unión `UiBlock` pequeña y extensible:

```python
@dataclass(frozen=True)
class NoticeBlock:
    id: str
    kind: Literal["info", "warn", "error"]
    message: str

@dataclass(frozen=True)
class KeyValueBlock:
    id: str
    title: str
    items: tuple[tuple[str, str], ...]

@dataclass(frozen=True)
class TodoItem:
    id: str
    title: str
    completed: bool = False
    detail: str | None = None

@dataclass(frozen=True)
class TodoListBlock:
    id: str
    title: str
    items: tuple[TodoItem, ...]

@dataclass(frozen=True)
class ProgressBlock:
    id: str
    label: str
    completed: int | None = None
    total: int | None = None
    detail: str | None = None
```

La primera versión permite publicar, reemplazar y eliminar bloques. Los TODOs son de solo visualización en el primer corte. Interacciones como marcar un TODO o pulsar acciones se dejan para una fase posterior, con acciones declarativas y dispatcher del plugin, no callbacks de widgets.

#### Preguntas/interacción

```python
@dataclass(frozen=True)
class Choice:
    id: str
    label: str
    detail: str | None = None

@dataclass(frozen=True)
class FormField:
    id: str
    label: str
    kind: Literal["text", "password", "integer"] = "text"
    required: bool = True
    default: str | None = None
    help: str | None = None

@dataclass(frozen=True)
class InteractionResult:
    status: Literal["submitted", "cancelled", "unavailable"]
    values: Mapping[str, str] = field(default_factory=dict)
```

```python
@runtime_checkable
class PluginUiService(Protocol):
    def publish(self, block: UiBlock) -> None: ...
    def replace(self, block_id: str, block: UiBlock) -> None: ...
    def remove(self, block_id: str) -> None: ...
    def set_status(self, key: str, label: str | None) -> None: ...

    async def confirm(
        self, *, title: str, message: str, danger: str | None = None
    ) -> InteractionResult: ...

    async def select(
        self, *, title: str, message: str, choices: Sequence[Choice]
    ) -> InteractionResult: ...

    async def form(
        self, *, title: str, fields: Sequence[FormField]
    ) -> InteractionResult: ...
```

El usuario nunca debe quedar bloqueado porque una UI no esté disponible. Cancelación por Esc/Ctrl+C/EOF retorna `status="cancelled"`; one-shot/CI retorna `status="unavailable"` y nunca intenta consumir stdin.

#### Contexto de comandos

```python
@runtime_checkable
class CliCommandContext(Protocol):
    plugin_name: str
    cwd: Path
    session_id: str
    ui: PluginUiService

    def notify(self, kind: Literal["info", "warn", "error"], message: str) -> None: ...
```

El protocolo será deliberadamente mínimo. No expone `CommandHandler`, `Renderer`, `PhosonApp`, `SessionController`, `ConversationTree`, `Rich Console` ni configuración mutable. Nuevas capacidades requieren una extensión explícita/versionada del protocolo.

### 3.2 Hooks opcionales en `Plugin`

Añadir al ABC existente defaults no disruptivos:

```python
class Plugin(ABC):
    # hooks actuales...

    def get_commands(self) -> list[CliCommandSpec]:
        return []

    def get_tool_render_specs(self) -> list[ToolRenderSpec]:
        return []

    def get_theme_extension(self) -> ThemeExtension | None:
        return None

    async def aclose(self) -> None:
        self.cleanup()
```

`close_plugins()` preferirá incondicionalmente `await plugin.aclose()`. Esto formaliza el hook que hoy es duck typing en `phoson_cli/session_utils.py`, conservando el comportamiento síncrono como default. `AgentEngine.cleanup()` permanece síncrono y llama `cleanup()` para su API existente.

### 3.3 Bootstrap y catálogo por sesión

`SessionController._rebuild_engine()` será la fuente de verdad:

1. Construye specs configurados por el usuario.
2. Construye los specs MCP existentes.
3. Carga todos mediante `AgentEngine`.
4. Con `engine._loaded_plugins`, valida y construye un `CliExtensionRegistry` **por controller**.
5. Expone ese registry a `CommandHandler`, completers, formateadores y resolución de temas.

El mismo helper de specs se usará en `_run_oneshot()`. One-shot carga tools/middlewares del plugin y sus extensiones no interactivas; las preguntas simplemente retornan `unavailable`.

En cada rebuild provocado por `/model`, `/provider` o cambios de MCP:

- se construye un registry nuevo;
- el handler y completer observan la nueva versión del registry;
- se descartan specs visuales del engine anterior;
- se cierran las instancias anteriores con `close_plugins()`.

### 3.4 Comandos dinámicos

Mantener `COMMAND_SPECS` como tupla nativa pública por compatibilidad, pero crear `CommandCatalog`:

```python
class CommandCatalog:
    native_specs: tuple[CommandSpec, ...]
    plugin_specs: tuple[RegisteredPluginCommand, ...]
    version: int
```

- Nativos primero en `/help` y completion.
- Los comandos de plugin se ordenan por categoría y luego nombre; `Plugins` es la categoría por defecto.
- `get_grouped_command_help()` y `get_command_help()` aceptan catálogo explícito.
- `SlashCompleter` recibe un provider/callback al catálogo actual; no lee solo el `COMMANDS` global.
- `CommandHandler` reconstruye dispatch cuando cambie `catalog.version`.
- Cada `RegisteredPluginCommand` conserva `plugin_name`, instancia y `CliCommandSpec` ya validado.

**Validación y colisiones:**

- Todos los nombres/aliases empiezan por `/`, no contienen espacios y son únicos dentro del spec.
- Un alias nativo está reservado y causa error de bootstrap.
- Una colisión entre dos plugins causa error de bootstrap que enumera ambos plugins y el alias.
- El método declarado debe existir, ser callable y retornar un awaitable.
- Los fallos de handler se convierten en notice/log y mantienen el REPL abierto; `asyncio.CancelledError` se propaga.

### 3.5 Registro visual de tools

`ToolRenderRegistry` tiene defaults nativos equivalentes a `_TOOL_VERBS` y specs de plugins para esa sesión.

- Una spec para una tool inexistente es error de configuración: evita typos silenciosos.
- Una plugin tool puede declarar su propio nombre; una spec que intenta cambiar una tool core requiere una decisión posterior. **v1 la rechaza**, para impedir que una dependencia cambie semántica visual core inesperadamente.
- `tool_verb()`, cabeceras y render de historial reciben el registry explícito o lo obtienen desde el contexto de render de la sesión; se elimina el estado global mutable.
- Las tools nativas conservan exactamente verbo, icono y render actuales.

### 3.6 Temas y orden de inicialización

Crear `ThemeRegistry` en `phoson_cli/theme.py`:

- Contiene los cuatro temas built-in y extensiones derivadas de plugins.
- Expone `get_theme(name)`, `valid_names()` y `load_theme(config_value, registry=...)`.
- `NO_COLOR`/`CLICOLOR=0` mantienen prioridad absoluta.
- `VALID_NAMES` continúa representando los cuatro built-ins por compatibilidad estática; comandos/pickers en runtime usan `registry.valid_names()`.
- `theme_picker.py` reemplaza `_THEME_ROWS` fijo por filas generadas del registry.

El orden actual debe ajustarse porque `PhosonRepl` y `PhosonApp` resuelven el tema antes de crear `SessionController`. El bootstrap será en dos fases:

1. cargar config y construir/cargar plugins;
2. construir registry de extensiones;
3. resolver `config.theme` usando ese registry;
4. crear/aplicar el frontend con el tema final.

Así `theme = "example-neon"` no emite un warning falso antes de que el plugin que lo declara haya cargado.

## 4. Gestión e instalación de plugins comunitarios

### 4.1 UX de CLI

La interfaz principal será un grupo de subcomandos:

```bash
phoson-cli plugin install <source>
phoson-cli plugin list
phoson-cli plugin enable <id>
phoson-cli plugin disable <id>
phoson-cli plugin remove <id>
phoson-cli plugin update <id>
phoson-cli plugin doctor [id]
```

Para la propuesta original se conserva un alias cómodo:

```bash
phoson-cli --install-plugin <source>
# equivalente a: phoson-cli plugin install <source>
```

El parser actual es manual (`phoson_cli/__main__.py::parse_args`), por lo que se añadirá un `plugin_command` estructurado a `CliOptions` sin añadir Click/Typer.

### 4.2 Formatos de source

Se aceptan:

```bash
# Recomendado: distribución con versión inmutable
phoson-cli plugin install "phoson-plugin-example==1.2.0"

# Atajo GitHub
phoson-cli plugin install github:phoson-lat/plugin-phoson-example@v1.2.0

# PEP 508 / pip estándar
phoson-cli plugin install \
  "phoson-plugin-example @ git+https://github.com/phoson-lat/plugin-phoson-example.git@v1.2.0"
```

`git:https://github.com/...` puede aceptarse como alias de entrada para la idea original, pero **no será el formato canónico**: se normaliza a un requirement estándar `git+https://...`. Esto evita crear una sintaxis propia difícil de interoperar.

No se recomienda instalar desde una rama mutable. Si el usuario omite tag/commit, el CLI debe resolver el SHA remoto, mostrarlo antes de instalar y persistirlo. `--yes` permite automatización explícita.

### 4.3 Instalación y persistencia

Crear un módulo dedicado, p. ej. `phoson_cli/plugin_manager.py`:

1. normaliza el source a un requirement PEP 508/direct URL;
2. pide confirmación, dejando claro que instalar un plugin ejecuta código Python con permisos del usuario;
3. instala en el entorno donde corre el ejecutable mediante `uv pip install --python <sys.executable> <requirement>`; si no hay `uv`, falla con instrucción explícita en vez de elegir silenciosamente otro intérprete;
4. inspecciona `importlib.metadata.entry_points(group="phoson.plugins")`;
5. exige al menos un entry point nuevo/identificable y valida que carga como `Plugin` en `plugin doctor`;
6. agrega una spec `entrypoint:<nombre>` a `PhosonConfig.plugins`, inicialmente `enabled`/presente;
7. persiste un lockfile para trazabilidad.

Propuesta de lockfile separado:

```toml
# ~/.phoson/plugins.lock.toml
[[plugin]]
id = "example"
distribution = "phoson-plugin-example"
version = "1.2.0"
source = "github:phoson-lat/plugin-phoson-example@v1.2.0"
requirement = "phoson-plugin-example @ git+https://github.com/...@v1.2.0"
resolved_commit = "8c4ef19a..."
entry_point = "example"
enabled = true
installed_at = "2026-08-30T00:00:00Z"
```

`config.toml` contiene solo declaración/configuración de runtime:

```toml
[defaults]
plugins = [
  { name = "entrypoint:example", config = { greeting = "Hola" } }
]
```

La instalación y el lockfile no sustituyen el uso manual de `plugins = [...]`; usuarios avanzados pueden declarar paquetes ya instalados, paths locales o entry points directamente.

### 4.4 Semántica de gestión

- `list`: muestra id, distribución, versión, source pinneado, entry point y estado.
- `enable`: agrega/reactiva la spec configurada; no reinstala.
- `disable`: quita/desactiva la spec de `config.toml`; no desinstala paquetes.
- `remove`: requiere confirmación; deshabilita y ejecuta `uv pip uninstall` de la distribución registrada. Si varias entradas comparten una distribución, exige selección/confirmación reforzada.
- `update`: muestra versión/source actual y destino, exige confirmación, actualiza lockfile y config sin borrar la configuración `config` del usuario.
- `doctor`: valida disponibilidad de distribución, entry point, carga del `Plugin`, compatibilidad declarada y conflictos de comandos/temas/specs, sin iniciar una sesión de agente.

### 4.5 Metadata y compatibilidad

Recomendar para plugins externos:

```toml
[project.entry-points."phoson.plugins"]
example = "phoson_plugin_example:create_plugin"

[project.entry-points."phoson.plugin_metadata"]
example = "phoson_plugin_example:metadata"
```

La metadata detallada es un enhancement opcional posterior. En v1, el entry point `phoson.plugins` es obligatorio y el CLI obtiene nombre/version desde `Plugin` y `importlib.metadata`; no se crea un segundo mecanismo de carga.

La documentación deberá fijar una matriz de compatibilidad basada en versión mayor del API de plugins cuando exista. Esta primera entrega puede incluir `requires_phoson` opcional en metadata, validado por `doctor` si está disponible.

## 5. Adaptadores de interacción por frontend

| Capacidad | Fullscreen | REPL clásico | One-shot / CI |
|---|---|---|---|
| `confirm` | modal `Float` | prompt `y/N` | `unavailable` |
| `select` | picker modal | selector numerado | `unavailable` |
| `form` | modal con campos | preguntas secuenciales | `unavailable` |
| `NoticeBlock` | bloque en chat | notice Rich | texto plano stdout |
| `KeyValueBlock` | card en chat | tabla/lista Rich | texto plano |
| `TodoListBlock` | card actualizable | lista Rich actualizable o reimpresa | texto plano |
| `ProgressBlock` | card/estado vivo | `Live`/línea compatible | texto final o no-op |
| `set_status` | activity/header | spinner/notice | no-op |

Implementación:

- Un `FullScreenPluginUiService` reutiliza el mecanismo existente de `PhosonApp.run_float_picker()`, `_open_float()` y `run_float_confirm()`.
- Un `ClassicPluginUiService` reutiliza prompt_toolkit/Rich, sin iniciar una segunda aplicación fullscreen.
- Un `NonInteractivePluginUiService` es explícito y seguro: no solicita stdin y retorna `unavailable`.
- Las operaciones de UI se serializan: un solo modal/interacción activa por sesión. Si ya existe una interacción, la siguiente espera mediante lock async o falla con mensaje claro según el contexto.
- Los inputs `password` no se guardan en transcript, logs, bloques UI ni estado persistido por defecto.
- Se definen límites de tamaño para título, mensaje, choices, campos y bloques, para proteger TUI/transcript ante output de modelo o plugins defectuosos.

Los servicios se inyectan en `engine.context.extra`, de manera análoga a `bash_confirmation`, `on_subagent_progress` y otros servicios actuales. Las tools de plugin que necesiten interacción deben declararlo en `@tool(inject=["plugin_ui"])` y manejar `None`/`unavailable` correctamente.

## 6. Plan de ejecución por PRs

### PR A — Contrato público y cierre asíncrono

**Objetivo:** fundación independiente del CLI.

**Archivos principales**

- Nuevo: `phoson_agent/cli_extensions.py`
- `phoson_agent/plugin.py`
- `phoson_agent/__init__.py`
- `phoson_cli/session_utils.py`
- `tests/phoson_agent/test_plugin_system.py`
- Nuevos tests de tipos/contratos.

**Cambios**

- Dataclasses y Protocols neutrales de comandos, tool render, temas, bloques e interacciones.
- Hooks opcionales en `Plugin`.
- `Plugin.aclose()` default que delega a `cleanup()`.
- `close_plugins()` usa `await plugin.aclose()` y captura fallos por plugin.

**Tests**

- Hooks default vacíos/no rompen los tres plugins oficiales.
- `aclose()` default llama exactamente una vez a `cleanup()`.
- Plugin con `aclose()` especializado lo usa al cerrar.
- Contratos no importan `phoson_cli`, `rich` ni `prompt_toolkit`.

### PR B — Config, specs unificados y lifecycle de runtime

**Objetivo:** hacer que plugins de usuario existan como configuración real en todos los modos.

**Archivos principales**

- `phoson_cli/config.py`
- `phoson_cli/session_utils.py`
- `phoson_cli/controller.py`
- `phoson_cli/__main__.py`
- `tests/phoson_cli/test_config_unit.py`
- `tests/phoson_cli/test_controller_unit.py`
- `tests/phoson_cli/test_oneshot_unit.py`

**Cambios**

- Añadir `plugins: list[str | dict[str, Any]]` a `PhosonConfig`.
- Validar que TOML contiene una lista cuyos miembros son string o tabla válida para `PluginSpec`.
- Extender `save_config()` con serialización TOML controlada de listas/dicts, preservando comentarios y contenido no gestionado.
- Crear `build_plugin_specs(config)` que mergea `[...config.plugins, ...MCP]` de forma documentada/determinista.
- Reusar el helper en controller y one-shot.
- Exponer plugins cargados a un punto de construcción de extensiones.

**Tests**

- Default vacío, file round-trip, config por string y dict, valores inválidos con error útil.
- El guardado parcial no reescribe accidentalmente `plugins`.
- Plugins config + MCP se cargan en orden documentado.
- One-shot carga un plugin configurado igual que el modo interactivo.
- Rebuild cierra instancias anteriores y no duplica extensiones.

### PR C — Catálogo y dispatch de comandos de plugin

**Objetivo:** comandos de comunidad con `/help` y completion correctos.

**Archivos principales**

- `phoson_cli/commands.py`
- `phoson_cli/repl.py`
- `phoson_cli/fullscreen/app.py`
- Posiblemente `phoson_cli/controller.py`
- Tests de commands, REPL y `fullscreen`.

**Cambios**

- `CommandCatalog`/`CliExtensionRegistry` por sesión.
- Dispatch nativo + plugins, con actualización versionada tras rebuild.
- `get_command_help` y help agrupado reciben catálogo.
- `SlashCompleter` consulta el catálogo actual dinámicamente.
- Dispatch seguro y errores presentados como notice.

**Tests**

- Comando de plugin se ve y ejecuta en clásico/fullscreen.
- `/help` agrupa correctamente una categoría de plugin y `Plugins` default.

## 7. Matriz de pruebas final

Además de los tests de cada PR:

1. Los plugins oficiales MCP/checkpoint/memory cargan y cierran sin cambios de código.
2. Un plugin de ejemplo instalado por entry point funciona en classic, fullscreen y one-shot.
3. Una conversación con plugin instalado permite cambiar `/model` y `/provider` sin duplicar tools/comandos/cards ni filtrar recursos.
4. Dos `SessionController` simultáneos con plugins/temas diferentes se mantienen aislados.
5. `/help`, autocomplete, `/theme list` y pickers reflejan exactamente el registry activo.
6. `NO_COLOR=1` nunca muestra colores, incluso para tema/card de plugin.
7. La instalación no toca `config.toml` ni lockfile si falla `uv pip install` o la validación de entry point.
8. `plugin doctor` no inicia una sesión de agente ni muestra UI; identifica un plugin deshabilitado o un paquete roto.
9. Ninguna operación one-shot intenta `input()` debido a una tool/plugin interactiva.
10. Ejecutar:

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run pyright
```

## 8. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Código remoto tiene permisos del usuario | Advertencia y confirmación obligatorias; source/version/SHA visibles; no auto-update; lockfile; docs explícitas: no es sandbox. |
| Source Git mutable deja instalaciones no reproducibles | Resolver y guardar commit SHA; recomendar tags/versiones; `update` siempre explícito. |
| Modificar el entorno de `phoson-cli` equivocado | `uv pip install --python sys.executable`; fallar explícitamente si `uv` no está disponible; mostrar intérprete/entorno destino. |
| Un plugin sobrescribe `/exit`, `/model` u otro core | Catálogo reserva nombres nativos y rechaza colisiones durante bootstrap. |
| Dos plugins reclaman el mismo alias/tema/tool spec | Validación determinista con ambos nombres en el error; no política "last wins". |
| Estado global filtra entre sesiones o tests | Registries por controller/sesión, no dicts mutables globales; reconstrucción versionada. |
| Rebuild recarga plugins y deja handlers a instancia cerrada | Handler/completer consultan catálogo con versión actual; cerrar runtime anterior solo después de construir/swap seguro del nuevo. |
| Tema plugin no se resuelve al arranque | Bootstrap en dos fases: plugins antes de resolución final del theme. |
| Plugin UI rompe fullscreen o clásico al importar widgets | Contratos neutrales en `phoson_agent`; adapters exclusivamente en `phoson_cli`. |
| Tool del LLM solicita demasiadas preguntas o filtra secretos | Una interacción modal por sesión, límites de tamaño, cancelación segura, fields password no persistidos/logueados. |
| One-shot queda esperando stdin | `NonInteractivePluginUiService` devuelve `unavailable`; tests obligatorios. |
| Persistencia de TODOs se mezcla con conversaciones | v1 solo bloque UI en memoria; si se añade estado durable será namespace por plugin/sesión, separado de JSONL. |

## 9. Decisiones que requieren confirmación antes de PR G/F

1. **Entorno de instalación:** el plan elige instalar en el entorno del ejecutable actual con `uv pip --python sys.executable`. Es la menor complejidad y permite que entry points sean visibles al proceso. Un venv aislado por plugin requeriría host/subproceso o manipulación de `sys.path`, y debe ser proyecto separado.
2. **Trust model:** v1 solo advierte/confirma; no hay firma, allowlist ni sandbox. Si se desea una política corporativa, definir `allowed_sources`/allowlist como issue separado.
3. **Acciones interactivas de TODO:** v1 publica TODOs y permite que el plugin los reemplace; checkboxes/botones accionables se posponen hasta que el dispatcher de `UiAction` tenga diseño y permisos propios.
4. **Render especializado:** el mínimo comprometido es verbo+icono. Los bodies complejos deben usar `UiBlock` neutral, no objetos Rich; confirmar si se incluye en PR D o se limita a PR F.
5. **Estado persistente por plugin:** no se habilita implícitamente. Si I-126 necesita persistencia para monitores, se diseñará un `PluginStateStore` explícito compatible con checkpoint, no un acceso libre a archivos de sesión.

## 10. Definición de listo de I-110

- Un usuario puede ejecutar `phoson-cli plugin install ...`, ver qué instaló, habilitar/deshabilitarlo, diagnosticarlo y desinstalarlo con origen/version/commit trazables.
- El mismo plugin se carga desde `config.toml` en fullscreen, REPL clásico y one-shot; MCP sigue funcionando.
- Un plugin de ejemplo, sin cambiar archivos bajo `phoson_cli`, aporta herramienta, comando slash, icono/verbo, tema, confirmación/formulario y TODO/progreso declarativo.
- `/help`, autocompletado y `/theme` muestran las extensiones activas y se refrescan correctamente tras rebuild.
- Plugins inválidos o con colisiones fallan temprano con mensajes claros; no hay comportamiento implícito "last wins".
- Las operaciones interactivas se cancelan o degradan con seguridad en hosts sin UI.
- Los tres plugins oficiales existentes pasan sus pruebas sin modificaciones.
- Suite completa, Ruff y Pyright están limpios; documentación explica packaging, instalación, configuración, lifecycle, compatibilidad y el modelo de seguridad.
