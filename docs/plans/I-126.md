# Plan I-126 — Plugin oficial `phoson_plugin_monitor`: monitores de larga duración que reactivan al agente

> **Issue:** [#126](https://github.com/phoson-lat/phoson-engine-minimal/issues/126) · **P2** · **L** (~3–4 días)
> **Rama:** `feat/i126-monitors-plugin` (convención: `feat/iNNN-descripcion`)
> **Estado:** ✅ **Implementado (v0.19.0)** — ver "Desviaciones del plan" al final.
> **Problema:** el engine es stateless-by-run: cuando `AgentEngine.run()` regresa, nada persiste ni se
> reprograma. No hay mecanismo first-class para "observa X y despiértame cuando pase Y": hoy
> requiere host code hackeado, y `phoson_http` (daemon mode) está pausado en el roadmap.
>
> **Decisión de diseño clave (resuelve la "core question" del issue):** **cola de wakes
> persistente como source of truth + callback `on_wake` opcional para hosts en vivo.**
> El plugin vive 100 % dentro del contrato `Plugin` existente (cero cambios en
> `phoson_agent`); la integración en `phoson_cli` es un hook duck-typed mínimo
> (~15 líneas) que deja al core minimal intacto.

## Hallazgos verificados en código (afinan la propuesta original)

1. **El contrato `Plugin` ya cubre todo lo que el plugin necesita**
   (`phoson_agent/plugin.py`): ciclo `configure()` → `initialize()` → uso → `cleanup()`,
   más `async def aclose()` (default delega en `cleanup()`). El plugin de monitores
   **no necesita un contrato de lifecycle nuevo** — lo confirma la sección "Canonical
   interface decision" de `docs/plugins.md`.
2. **`load_plugin()` SIEMPRE llama `configure(spec.config)` y luego `initialize()`**
   (`phoson_agent/plugin_loader.py:136-138`), también para instancias directas. El plugin
   puede asumir que `initialize()` corre exactamente una vez por engine.
3. **El engine se reconstruye con `/model`, `/provider` y `/mcp`** —
   `SessionController._rebuild_engine()` (`phoson_cli/controller.py:~326`) cierra los
   plugins viejos (`close_plugins` → `aclose()`) y construye un `AgentEngine` nuevo.
   **Consecuencia crítica:** las tareas asyncio del plugin mueren en cada cambio de
   modelo/provider. El diseño debe tratar **el estado en disco como source of truth y
   las tareas in-memory como caché re-derivable** ("self-healing"): `initialize()`/
   `ensure_started()` resucitan los monitores "running" desde disco. Precedente: el MCP
   plugin reconecta pools igual en cada rebuild.
4. **Los plugins in-tree son singletons por módulo** (`phoson_plugin_checkpoint/__init__.py`
   exporta `plugin = CheckpointPlugin()`; el package loader hace `importlib` +
   `getattr(module, "plugin")`). El fallback `path:./phoson_plugin_monitor/_plugin.py`
   (patrón de `build_mcp_plugins`, `session_utils.py:154-178`) crea una instancia nueva por
   rebuild vía `create_plugin()`. En ambos casos el orden es seguro: se cierra el plugin
   viejo ANTES de construir el engine nuevo → no hay dos tareas vivas para el mismo monitor.
5. **`initialize()` puede correr sin event loop** (`_rebuild_engine` desde `__init__`):
   `asyncio.create_task` fallaría. El plugin debe **arrastrar el arranque de tareas hasta
   un contexto async**: método público idempotente `ensure_started()` que el host `await`ea,
   más arranque perezoso en la primera tool call (los handlers de tool son async → el loop
   existe). Esto es el mismo patrón que `aclose()` ya impone para el cierre.
6. **Inyección de `session_id`:** el CLI guarda la sesión en `self._session.tree.session_id`
   (`controller.py:203,775,829,1030-1033`), pero `new_session()`/`load_session()` cambian el
   tree **sin reconstruir el engine** → un valor estático en `context.extra` quedaría stale.
   Solución: inyectar un **callable** `engine.context.extra["session_id_provider"] = lambda:
   self._session.tree.session_id` (1 línea, siempre fresco); la tool lo recibe con
   `@tool(inject=["session_id"])` (kw-only, excluido del schema JSON — mecánica ya probada en
   `subagent.py` con `_AGENT_INJECT`) y lo invoca en el momento del registro. Fallback:
   config `default_session_id` o `""` (el wake se queda "sin sesión" y el host decide).
7. **Los wakes necesitan entrar al próximo run del CLI:** `run_turn()`
   (`controller.py:738`) es el único punto donde el usuario genera un run — ahí se hace el
   drain: `pending_wakes(session_id)` → se combinan como header en el user message
   (`[Monitor events] …`) antes del input del usuario. Combina en un solo mensaje (no un
   nodo de tree por wake) para no ensuciar la `ConversationTree`; un nodo por wake queda
   como follow-up. El hook es duck-typed (`hasattr(plugin, "drain_pending_wakes")`):
   cero contratos nuevos en `phoson_agent`.
8. **`plugin_ui` ya está inyectado por el CLI** (`controller.py:~407`:
   `context.extra["plugin_ui"] = SinkPluginUiService(...)`), y `CliCommandContext` expone
   `session_id`, `ui` y `notify()` (`cli_extensions.py`). → El plugin puede exponer
   **`/monitors`** vía `get_commands()` (infraestructura de I-110, ya shipped en v0.18.0)
   con `KeyValueBlock` de estado, sin tocar `phoson_cli`. Los hosts no-interactivos
   devuelven `InteractionResult(status="unavailable")` — el plugin debe manejarlo.
9. **Patrones de storage a reusar:** `JsonlStorage` (`phoson_agent/sessions/storage_jsonl.py`)
   demuestra write atómico (tmp + fsync + `os.replace`), `asyncio.to_thread` para no bloquear
   el loop, y parse leniente de líneas corruptas (`_read_session_meta`). `phoson_plugin_checkpoint`
   demuestra el wiring de un storage "propio" en el ciclo `Plugin`. El monitor usa **solo
   stdlib** (json, pathlib, asyncio, datetime, uuid, fnmatch): sin dependencias nuevas.
10. **`@tool` + `Literal` ya genera `enum` en el schema JSON**
    (`tool.py::_json_schema_for_type`): `kind: Literal["interval", "file"]` →
    `{"type": "string", "enum": ["interval", "file"]}`. Descripciones por parámetro vía
    `Annotated[dict, "…"]` (precedente I-127). Un `spec` libre (`dict`) esquematiza como
    `{"type": "object"}` y se valida por kind en el handler con errores legibles para el LLM.
11. **Tests:** `asyncio_mode = "auto"` en `pyproject.toml`; el patrón de fakes es
    `FakeToolChat(BaseLLMChat)` (`tests/phoson_agent/test_agent_engine_integration.py:88`) para
    e2e sin proveedor, y el patrón de integración es
    `tests/phoson_plugin_checkpoint/test_postgres_storage.py` (skip-if-unavailable con
    `pytest.mark.skipif`). Para determinismo, los kinds inyectan su función de sleep/clock
    (fake clock) en tests; 1 test de integración con reloj real.
12. **Opt-in por config (precedente `enable_mcp`):** un plugin con tareas en segundo plano
    NO debe activarse por defecto en la CLI. Se añade `enable_monitors: bool = False`
    (+ env `PHOSON_ENABLE_MONITORS`) a `PhosonConfig` y `build_monitor_plugins(config)` en
    `session_utils.py` que replica `build_mcp_plugins` (in-tree primero, fallback
    `path:./phoson_plugin_monitor/_plugin.py`). En la API de Python (`AgentEngine`) el
    plugin siempre está disponible al agregarlo a `plugins=[...]`.

## Decisiones de diseño

### 1. Wake: cola persistente + callback opcional (la combinación que propone el issue)

- **Cola = source of truth.** Cada fire apende un `WakeEvent` a `wake.jsonl`.
  Sobrevive a crashes y reinicios; es auditable por el usuario.
- **`on_wake` opcional** vía `configure({"on_wake": callable})`: se invoca con el
  `WakeEvent` cuando hay un host en vivo (p. ej. Phoson-Core embebido). El host decide
  si dispara un `run()` inmediato. El CLI v1 **no** lo usa (el drain en `run_turn` cubre
  la reactivación al próximo turno del usuario); el ejemplo de host autónomo va en
  `examples/`.
- **Mientras un run está activo:** el fire se queda en la cola (y, si hay `plugin_ui`,
  el plugin publica un `NoticeBlock` informativo). No se inyecta mid-run: el engine no
  tiene canal de inyección de mensajes durante un run (y no se añade en este issue).

Flujo (CLI):

```
monitor task (host loop)            wake.jsonl                 run_turn()
      │  condición cumple                 │                           │
      ├─ fire: apende WakeEvent ─────────►│                           │
      ├─ (opcional) plugin_ui notice      │                           │
      │  … host idle …                    │      user tipea ─────────►│
      │                                   │   drain pending_wakes(sid)│
      │                                   │◄──── mark consumed ───────┤
      │                                   │   [Monitor events] + input► AgentEngine.run()
```

### 2. Persistencia (stdlib, minimal)

Directorio por config (`data_dir`, default `~/.phoson/monitors/`):

| Archivo | Contenido | Escritura |
|---|---|---|
| `monitors.json` | Registry: `{version, monitors: [{name, kind, spec, created_at, state: running/stopped, session_id, last_fired_at, last_check_at, stats}]}` | Atómica (tmp + fsync + `os.replace`) en cada mutación |
| `wake.jsonl` | Cola de fires: `{id, monitor, session_id, fired_at, payload, consumed}` | Apend 1 línea + flush; consume = re-escritura atómica marcando `consumed` |

- Parse leniente (línea truncada al final por crash → se descarta con log, patrón
  `_read_session_meta`).
- **Semántica de crash:** proceso muere → tareas mueren, pero `monitors.json` sigue
  diciendo `running` → el próximo `initialize()`/`ensure_started()` **resucita** los
  monitores. Los wakes pendientes sobreviven y se drenan.
- Un solo writer por `data_dir` (documentado). Lock file con PID = follow-up.

### 3. Kinds de la v1

| Kind | Spec | Fire cuando | Esfuerzo |
|---|---|---|---|
| `interval` | `{seconds, once?}` | Pasan N segundos (o una vez) | trivial (loop `sleep`) |
| `file` | `{path, glob?, event: created\|changed\|both, poll_seconds?}` | Aparece/cambia (mtime/size) el path o algún glob | polling con `stat` — **sin inotify** (cross-platform, sin deps) |

- `command` (interval + fire en exit≠0 o cambio de output) → **stretch de este mismo
  PR** (valida el path de cleanup de subprocess en `aclose()`).
- `http` → **fuera de scope** (depende del daemon `phoson_http` pausado; httpx ya es
  dependency, pero ampliar surface en la v1 diluye el PR).
- **Seguridad de `command`:** el registro es una tool call del LLM → pasa por el
  `PermissionMiddleware` con los args visibles (el usuario aprueba el comando exacto al
  registrar). El registry guarda el hash del comando; ejecutar = repetir lo aprobado.
  Documentado en el README.
- **Anti-storm v1:** cooldown implícito por kind (un `interval` no dispara dos veces en el
  mismo período; `file` solo en cambio real de mtime/size) + `max_pending_wakes_per_monitor`
  (default 5; al exceder, se descarta el más viejo y se anota en el `payload` del nuevo).

### 4. Tools (vía `get_tools()`, schemas JSON con `@tool`)

```python
@tool
async def register_monitor(
    name: str,
    kind: Literal["interval", "file"],          # enum en el schema
    spec: dict[str, Any],                        # campos por kind, validados
    *, session_id_provider: Callable[[], str] | None = None,  # inject, oculto
) -> str: ...

@tool
async def list_monitors() -> str: ...            # tablas JSON: state, last_fired, pending wakes
@tool
async def stop_monitor(name: str) -> str: ...    # cancel task + state=stopped (persiste)
```

- Devoluciones en texto plano legible por el LLM (precedente: tools del repo).
- Errores de validación de `spec` como string con el campo exacto (el LLM autocorrige).

### 5. Lifecycle del plugin

| Hook | Comportamiento |
|---|---|
| `configure(cfg)` | Lee `data_dir`, `on_wake`, `max_pending_wakes_per_monitor`, `default_session_id`. Valida `on_wake` (callable o ausente). |
| `initialize()` | Crea dir, carga `monitors.json` + `wake.jsonl` en memoria. **No crea tareas** (puede no haber loop). Marca monitores `running` como "deben correr". |
| `ensure_started()` (público, idempotente) | `await`eado por el host con loop vivo: `create_task` por monitor pendiente. También se invoca perezosamente desde cada tool handler. |
| tool handlers | Registro/detención persisten de inmediato; arrancan/cancelan la task en vivo. |
| fire interno | Apende `WakeEvent` → reescribe `wake.jsonl` (si cap excedido, compacta) → invoca `on_wake` en `create_task` (falla → log, nunca rompe el fire) → `NoticeBlock` si hay `plugin_ui`. |
| `aclose()` (override) | Cancela todas las tareas (y subprocesses si hay `command`), espera cancelación, flush final del registry. **No** marca `state=stopped` — los monitores siguen "running" en disco y se resucitan en el próximo host. |
| `cleanup()` (sync) | No-op deliberado (el cierre async es `aclose()`). Si el host solo llama `cleanup()`, las tareas mueren al morir el proceso; documentado. |
| `get_commands()` | `/monitors` (y `/monitors <name>`): lista estado + wakes pendientes vía `ctx.ui.publish(KeyValueBlock)` / `ctx.notify`. |

## Riesgos

1. **Rebuild del engine mata las tareas** (`/model`, `/provider`, `/mcp`) → mitigado por
   diseño: estado en disco + resurrección en `ensure_started()` (el controller la llama
   tras cada rebuild). Test específico: rebuild con monitor vivo → sigue corriendo.
2. **`initialize()` sin loop** → arranque perezoso doble vía (`ensure_started()` del host
   + perezoso en tool handlers). Documentado en el README del plugin.
3. **Wake storm** (monitor que dispara en loop) → cooldown por kind + cap de pending por
   monitor (default 5) + el fire más viejo se descarta, no se bloquea.
4. **Dos procesos escribiendo el mismo `data_dir`** (CLI + embed concurrentes) → v1
   documenta "un writer por data_dir"; lock con PID = follow-up (mismo alcance que el
   daemon de `phoson_http`).
5. **`command` kind ejecuta shell fuera del gate de permisos del run** → solo stretch;
   el registro (tool call del LLM) sí pasa por `PermissionMiddleware`, el hash del
   comando se valida en cada fire, y el README documenta la confianza requerida.
6. **Scope creep** (kinds `http`, inotify, daemon) → explícitamente fuera de la v1; el
   diseño de `spec: dict` + interfaz `run()` de los kinds deja la puerta abierta sin
   tocar el contrato.

## Desviaciones del plan (decisiones tomadas en implementación)

1. **Wake queue: rewrite atómico, no apend.** El plan decía "apend 1 línea + flush" con
   parse leniente. Al implementarlo se vio que el cap anti-storm **descarta un evento ya
   escrito en disco**, y un apend lo **resucitaría** en el próximo load. Como la cola
   está acotada (cap × monitores), cada mutación ahora **reescribe el archivo de forma
   atómica** (tmp + fsync + `os.replace`). El reader sigue siendo leniente (defensa en
   profundidad). El test `test_cap_survives_reload` cierra este caso.
2. **`kind` como `Literal` en la firma de `register_monitor`.** El plan lo dejaba como
   `str` validado en el handler. Con `Literal["interval","file","command"]` el
   `@tool` genera un `enum` en el schema JSON (mejor para el LLM) y la validación queda
   reforzada a dos niveles (schema + `validate_spec`).
3. **Timeout de `command`: kill del *grupo* de proceso.** El plan decía "kill del
   subprocess". Al probarlo, `sh -c "sleep 30"` deja al hijo `sleep` con la pipe abierta
   tras un `proc.kill()`, y el drain `communicate()` cuelga hasta EOF (reproducido de
   forma aislada). Solución: `start_new_session=True` + `os.killpg(..., SIGKILL)` en
   POSIX (fallback a `proc.kill()` en Windows), más un segundo `communicate()` bounded.
4. **`build_monitor_plugins` devuelve una instancia pre-configurada** (forma directa
   `Plugin`), no un dict con `instance`: `PluginSpec.from_value` descarta claves extra
   del dict (`instance`), así que el config no llegaría al plugin. La instancia es
   *fresh* (nunca el singleton de módulo) para que los rebuilds no compartan estado.
5. **`session_id_provider` inyectado en todos los rebuilds** (no solo con plugin), y
   `ensure_started()` programado como `create_task` dentro de `_rebuild_engine` con
   fallback `RuntimeError` para bootstraps sin loop. El test
   `test_ensure_started_runs_on_rebuild` cierra el caso de resurrección en `/model`.
