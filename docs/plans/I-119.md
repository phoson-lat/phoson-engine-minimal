# Plan I-119 — Degradar attachments `file://` muertos en vez de crashear la carga de sesión

> **Issue:** [#119](https://github.com/phoson-lat/phoson-engine-minimal/issues/119) · **P1** · **S** (~1–1.5 h)
> **Rama:** `fix/i119-missing-attachment-fallback` (convención: `fix/iNNN-descripcion`)
> **Problema:** una sesión con un attachment guardado en `/tmp` (`file:///tmp/shot-accepted.png`)
> crashea al reabrirse (`--resume`/load) con `FileNotFoundError`: el SO ya limpió el archivo y la
> re-conversión de mensajes para el próximo `llm.stream()` intenta re-leerlo.
> Trace: `summarizer._call_with_context_rescue` → `wrap_llm_call` → `stream()` →
> `_convert_content_block` → `load_file_as_base64` → `open()` → `FileNotFoundError` sin catcher.

## Hallazgos verificados en código (amplían la propuesta original del issue)

1. **El crash no está en 1 sitio, está en 6** (todos hacen `open()` sobre la ruta `file://`
   sin chequear existencia):
   | Adapter | Bloque | Línea | Lectura |
   |---|---|---|---|
   | `_openai_compatible.py` | `ImageBlock` | :118 | `load_file_as_base64(path, block.media_type)` |
   | `_openai_compatible.py` | `AudioBlock` | :131 | `open(path, "rb")` **crudo** (no usa el helper) |
   | `anthropic.py` | `ImageBlock` | :77 | `load_file_as_base64(path).split(",", 1)` |
   | `anthropic.py` | `DocumentBlock` | :99 | `load_file_as_base64(path).split(",", 1)` |
   | `gemini.py` | `ImageBlock` | :76 | `load_file_as_base64(source[7:]).split(",", 1)` |
   | `gemini.py` | `DocumentBlock` | :83 | `load_file_as_base64(block.source[7:]).split(",", 1)` |
   El sitio del traceback del issue es el primero, pero el bug es igual en los otros 5.
   `VideoBlock`/`AudioBlock` en Anthropic y `VideoBlock`/`DocumentBlock` en OpenAI-compat
   **no leen archivo** (ya son placeholder de texto) → no están afectados.
2. **Cuello de botella único:** `load_file_as_base64()` (`phoson_llm/utils.py:81`) lo usan
   5 de los 6 sitios. Si se fixea ahí + se enruta el `open()` crudo del `AudioBlock`
   OpenAI-compat por el helper, se cubre el 100% de los casos con una sola semántica nueva.
3. **La conversión corre *dentro* de la llamada LLM** (síncrona, en el path de `stream()`),
   ni en load de sesión ni en el summarizer hay guard que pueda atrapar un error de I/O de
   archivo → **el fix obligatorio está en la capa de conversión**, no arriba.
4. **`/tmp` es el caso típico, no el único:** cualquier attachment cuyo archivo se borre/mueva
   (limpieza manual, reboot con tmpfs, `--resume` en otra máquina). Los bloques se persisten
   en el historial tal cual (`attachments.py:112-124` crea `file://{path_resuelto}`); el
   archivo no sobrevive al run.
5. **Precedente de degradación a texto ya existe** en los 3 adapters: bloques no soportados
   se convierten en bloques de texto visibles (`[Video not directly supported by this
   provider: …]`, `[Unsupported block: …]`, `[Audio not supported by Gemini: …]`).
   Degradar un `file://` muerto a texto es consistente con el patrón existente.
6. **`utils.py` no tiene `logger`** — se añade `logger = logging.getLogger(__name__)`
   (el `logging` del engine/CLI ya está configurado por la app; el criterio "nada en stderr"
   se cumple porque deja de propagarse excepción, no porque se silencie el logger).

## Decisiones de diseño

- **Fix central en `load_file_as_base64()`** — cambio de contrato:
  ```python
  def load_file_as_base64(path: str, media_type: str | None = None) -> str | None:
      """… Returns None (and logs a warning) when the file is missing or unreadable."""
  ```
  - Catch `OSError` (cubre `FileNotFoundError`, `PermissionError`, `IsADirectoryError`,
    symlink roto), `logger.warning("attachment file missing or unreadable, degrading to "
    "text placeholder: %s", path)` → return `None`. **Nunca** re-raise.
  - Fuentes `data:` y `https://` no tocan este path → sin cambios.
- **Placeholder con formato único** vía helper nuevo en `phoson_llm/utils.py`
  (los 6 call sites rinden el mismo texto; los tests asertan la cadena exacta):
  ```python
  def missing_attachment_placeholder(kind: str, path: str) -> str:
      name = Path(path).name or path
      return f"[{kind} no longer available: {name}]"
  ```
  p. ej. `[image no longer available: shot-accepted.png]`,
  `[audio no longer available: voice.wav]`, `[document no longer available: spec.pdf]`.
- **Call sites** (forma idéntica en los 3 adapters):
  ```python
  if source.startswith("file://"):
      path = source[7:]
      data = load_file_as_base64(path, ...)   # str | None
      if data is None:
          return {"type": "text", "text": missing_attachment_placeholder("image", path)}
  ```
  - `AudioBlock` en `_openai_compatible.py`: enrutar el `open()` crudo por el helper
    (`data.split(",", 1)[-1]`), preserving `format` de hoy.
  - Gemini: placeholder vía `types.Part.from_text(text=…)` (misma API que usan sus
    placeholders actuales).
- **Descartado: sanitizar el historial en load de sesión** (reemplazar bloques antes de
  guardar/cargar). Razones: (a) mutaría historial persistido (destructivo); (b) vive en
  `phoson_cli`, pero el bug es del engine — cualquier usuario de librería que re-envíe
  mensajes viejos crashea igual; (c) el fix en conversión cubre *todos* los entry points
  (resume, summarize, resubmit manual) de una vez.
- **Sin cambios en `phoson_cli/attachments.py`:** validar existencia en *envío* (hoy
  `FileNotFoundError` con mensaje claro) sigue siendo correcto; solo cambia el lado carga.

## Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Cambio de contrato `str → str \| None` rompe callers futuros invisibles | Grep confirma los 5 callers; pyright (basic, estricto en el repo) detecta usos sin chequeo de `None` en el mismo PR. |
| Placeholder confuso para el modelo | El texto es explícito y consistente con los placeholders existentes; el modelo ve "no longer available" y no alucina el contenido. |
| Warning spam si la sesión tiene N attachments muertos | 1 warning por archivo por conversión (no por retry); es un evento legítimo de debugging. Si molestara, sería un follow-up (rate-limit del logger), fuera de scope. |
| Rutas relativas / `~` en `file://` | El attachments manager siempre resuelve a absolute; la semántica de existencia de `open()` se conserva idéntica (el catch no cambia cómo se resuelve). |
