# Plan I-127 — Timeout configurable por invocación en `bash` y en los sub-agents

> **Issue:** [#127](https://github.com/phoson-lat/phoson-engine-minimal/issues/127) · **P1** · **S-M** (~1.5–2 h)
> **Rama:** `feat/i127-per-call-timeouts` (convención: `feat/iNNN-descripcion`)
> **Problema:** la tool `bash` mata todo comando a los 30 s (`DEFAULT_TIMEOUT_SECONDS`,
> `phoson_cli/tools/bash.py:22`) y el LLM no puede subir ni bajar el timeout: el schema que
> ve solo expone `command`, así que un `pytest`/`pip install`/`docker build` — o un
> entrenamiento — que tarda >30 s se mata con `Command timed out after 30s`.
> **Extensión (acordada con el owner):** el mismo control por invocación se aplica a
> `agent`/`agents` (sub-agents): hoy su timeout (default 300 s) solo es configurable por
> `config.toml`/env y es invisible al LLM.
>
> **Decisión de diseño clave: SIN tope máximo.** El owner quiere libertad total para runs
> largos (p. ej. entrenamiento de un modelo). El escape ante un hang es la cancelación
> manual del run (Esc, path de I-108), no un cap.

## Hallazgos verificados en código (afinan la propuesta original)

### bash

1. **El soporte ya existe a un nivel de más bajo:** `_run_bash(command, safe_mode,
   timeout=DEFAULT_TIMEOUT_SECONDS, confirmation)` (`bash.py:36-40`) ya acepta timeout y
   ya implementa el path de kill completo: `asyncio.wait_for(proc.communicate(),
   timeout=timeout)` → `proc.kill()` + drain + `f"Command timed out after {timeout:.0f}s"`
   (el formato `:.0f` ya maneja cualquier valor). **No hay que tocar `_run_bash`.**
2. **El wrapper `@tool bash` (`bash.py:85-92`) es el único punto ciego:** llama a
   `_run_bash` sin `timeout` → cae al default 30 s. El fix es plomada a nivel tool layer:
   1 parámetro + sanitizar + forward.
3. **Detalle del issue corregido:** el body dice que el schema "expone `command` y
   `safe_mode`", pero `safe_mode` está en `inject=[...]` → `_build_parameters`
   (`phoson_agent/tool.py`) lo **excluye** del schema (el test existente
   `test_bash_tool_schema_hides_injected_params` lo aserta). El schema de hoy es
   `{properties: {command}, required: [command]}`; con el cambio será
   `{properties: {command, timeout}, required: [command]}`.
4. **Mecanismo de descripción del parámetro:** el `@tool` no usa el docstring para
   parámetros (solo `fn.__doc__` para la tool); las descripciones por parámetro salen de
   **`Annotated[float, "…"]`** — `tool.py::_json_schema_for_type` extrae el `str` de los
   `Annotated args` y lo pone en `prop["description"]`. Precedente de parámetro opcional:
   `read_file(start_line, end_line)`.
5. **Risk nuevo al quitar el cap (documentado, mitigado por diseño):** un comando
   *interactivo* que espera stdin (`git add .` sin `-A`, `ssh` sin contraseña, prompt
   `y/n` heredando el TTY) ya no muere a los 30 s y podría colgarse. Mitigación: **Esc
   cancela el run en vuelo** (ya existe, I-108). No se añaden detectores de prompt ni
   caps: la libertad es el requisito.

### sub-agents (hallazgos nuevos para la extensión)

6. **El timeout del subagent ya existe y es por config, no por LLM:**
   `PhosonConfig.subagent_timeout_seconds: float = 300.0` (`config.py:85`, resuelto desde
   env `PHOSON_SUBAGENT_TIMEOUT` / `config.toml` en `config.py:506-511`, persistido en
   `config.py:671`) → `controller.py:382-384` lo inyecta a `engine.context.extra` →
   `agent` y `agents` lo reciben como **kw-only inject** (`_AGENT_INJECT`/`_AGENTS_INJECT`,
   `subagent.py:500-510`) → invisible al LLM.
7. **Semántica existente: `0` = sin timeout.** `_run_one_subagent` (`subagent.py:435`):
   `if timeout_seconds is not None and timeout_seconds > 0: wait_for(...) else: run
   sin timeout`. Igual en `agents`'s `_attempt` (`if subagent_timeout_seconds > 0`). El
   nuevo parámetro **debe preservar esta semántica** (0 = desactivar), no tratarla como
   inválida.
8. **Dos paths a tocar en `subagent.py`:** `agent` → `_run_one_subagent(timeout_seconds=…)`
   (con su `except TimeoutError` → mensaje), y `agents` → `_attempt` inline con
   `asyncio.wait_for` + `except TimeoutError` → error `"timeout after {…:g}s"` por task.
9. **El caso entrenamiento exige AMBOS cambios:** `agent(task=…, timeout=14400)` para el
   wrapper externo y `bash(timeout=14400)` en el comando interno del subagent — sin el
   cambio de bash, el comando interno moría a los 30 s aunque el subagent tuviera 4 h.

## Decisiones de diseño

### Helper compartido (`phoson_cli/tools/_timeouts.py`, nuevo)

```python
def sanitize_timeout(value: object, default: float, *, allow_zero: bool = False) -> tuple[float, str | None]:
    """Validate a model-provided timeout (per-call override).

    Returns ``(effective_seconds, note)``. ``note`` is a short human/model-readable
    line to prepend to the tool result, only when the input was not usable.
    No upper bound by design: long-running jobs (training, big builds) are
    legitimate; the manual run-cancellation (Esc) is the safety net.
    """
```

| Input | `allow_zero=False` (bash) | `allow_zero=True` (subagent) |
|---|---|---|
| `300` / `300.0` / `"300"` | `300.0`, sin nota | `300.0`, sin nota |
| `0` / `"0"` | `default` + nota `invalid …; using default` | `0.0`, sin nota (**sin timeout**, semántica existente) |
| `-5`, `NaN` | `default` + nota | `default` + nota |
| `"abc"`, `None`, `True`/`bool` | `default` + nota | `default` + nota |

- `try: float(value) except (TypeError, ValueError)` → fallback (algunos modelos envían
  strings a pesar del schema `number`). `bool` se rechaza explícito (`float(True)==1.0`
  no es un timeout legítimo).
- `not seconds > 0` captura `≤ 0` **y** `NaN` (comparaciones con NaN son falsas).

### bash (`phoson_cli/tools/bash.py`)

```python
@tool(inject=["safe_mode", "bash_confirmation"])
async def bash(
    command: str,
    timeout: Annotated[float, TIMEOUT_DESCRIPTION] = DEFAULT_TIMEOUT_SECONDS,
    safe_mode: bool = False,
    bash_confirmation: ConfirmationService | None = None,
) -> str:
    """Execute a bash command and return stdout+stderr combined."""
    value, note = sanitize_timeout(timeout, DEFAULT_TIMEOUT_SECONDS)
    result = await _run_bash(
        command, safe_mode=safe_mode, timeout=value, confirmation=bash_confirmation
    )
    return f"{note}\n{result}" if note else result
```

- **Default = `DEFAULT_TIMEOUT_SECONDS` (30.0, no `None`):** el comportamiento omitido es
  bit-a-bit idéntico al de hoy.
- **`TIMEOUT_DESCRIPTION`** (texto que ve el LLM, corto por costo de prompt):
  `"Hard timeout in seconds. Defaults to 30. Raise for long-running "
  "builds/tests/training (no maximum)."
  " Commands that would wait for input must be made non-interactive."`
- `timeout` **no** va en `inject` (es parámetro del modelo). `allow_zero=False`
  (bash no soporta "sin timeout": un shell sin bound es el caso de hang más probable).
- Nota se **prepending** al resultado (el modelo la lee primero) y solo cuando hubo
  sanitize → salida limpia en el 99% de los casos.
- **Sin cambios en** `_run_bash`.

### sub-agents (`phoson_cli/tools/subagent.py`)

Nuevo parámetro **visible al LLM** en ambos wrappers, kw-only `subagent_timeout_seconds`
**se queda en inject** (sigue siendo el *default* de config; backward compatible con
`config.toml`/env y con tests existentes que pasan `subagent_timeout_seconds` por context):

```python
@tool(inject=_AGENT_INJECT)
async def agent(
    task: str,
    tools: list[str] | None = None,
    model: str | None = None,
    timeout: Annotated[float | None, SUBAGENT_TIMEOUT_DESCRIPTION] = None,
    *,
    chat: BaseLLMChat,
    ...
    subagent_timeout_seconds: float = 300.0,   # default de config (injected)
    ...
) -> str:
    effective, note = _resolve_subagent_timeout(timeout, subagent_timeout_seconds)
    ...
    content, fallback_used = await _run_one_subagent(..., timeout_seconds=effective, ...)
    return f"{note}\n{...}" if note else ...
```

```python
def _resolve_subagent_timeout(
    timeout: float | None, configured_default: float
) -> tuple[float, str | None]:
    if timeout is None:
        return configured_default, None
    return sanitize_timeout(timeout, configured_default, allow_zero=True)
```

- Semántica final: **omitido/`None`** → default de config (300 s o el del usuario) ·
  **`> 0`** → ese valor, sin tope · **`0`** → sin timeout (semántica existente) ·
  **`< 0`/NaN/inválido** → default de config + nota.
- `Annotated[float | None, …]`: el schema generator (`tool.py`) descarta el `None` del
  union → `{"type": "number", "description": …}`, default `None` → fuera de `required`.
- **`agent`:** `timeout_seconds=effective` en `_run_one_subagent` (su `except TimeoutError`
  y el log `%.0fs` ya manejan cualquier valor).
- **`agents`:** `effective` se resuelve una vez al inicio y se usa en el `_attempt`
  inline (`if effective > 0: wait_for(...)` — la condición ya existe) y en el mensaje de
  error `f"timeout after {effective:g}s"` (con `effective == 0` el `TimeoutError` no
  puede dispararse).
- **`SUBAGENT_TIMEOUT_DESCRIPTION`:**
  `"Optional hard timeout in seconds for the sub-agent run. Omit to use the "
  "configured default (300s). Raise for long-running tasks (no maximum). "
  "0 disables the timeout entirely."`
- Nota (solo en inválidos) se prepending al string retornado (en `agents`, al resumen).

## Plan de tests

### `tests/phoson_cli/test_bash_tool.py` (extensión)

1. **Default inalterado (regresión):** `bash.handler({"command": "echo hi"})` sin
   `timeout` funciona (tests existentes siguen verdes); `bash.parameters["required"] ==
   ["command"]` y `"timeout" not in required`.
2. **Schema expuesto (criterio del issue):** `props["timeout"]["type"] == "number"` y la
   descripción contiene `"timeout in seconds"`, `"30"` y `"no maximum"`.
3. **Forward del override (monkeypatch de `bash_module._run_bash`):** `handler({"command":
   "x", "timeout": 120})` → el fake recibe `timeout == 120.0`.
4. **Sanitización vía handler (mismo fake):** `-5` → `30.0` + nota; `0` → `30.0` + nota
   (`allow_zero=False`); `"abc"` → `30.0` + nota; `999999` → `999999.0` **sin nota**
   (sin tope: se respeta, no se clampa).
5. **e2e real (wire completa, rápido):**
   - `handler({"command": f'{sys.executable} -c "import time; time.sleep(1.2)"', "timeout": 5})`
     → exita con output normal.
   - `handler({"command": f'{sys.executable} -c "import time; time.sleep(2)"', "timeout": 0.5})`
     → contiene `"timed out"`.
6. **`_timeouts.py` unitarios directos:** casos de la tabla (incl. `NaN`, `True`, `"0"`
   con `allow_zero` True/False, `None`).

### `tests/phoson_cli/test_subagent_tool.py` (extensión; fakes ya existen)

7. **Schema de `agent` y `agents`:** `timeout` presente (`number`, descripción con
   `"300"`/`"0 disables"`), no requerido; `subagent_timeout_seconds` sigue ausente del

8. **Default por config (invariante):** `agent.handler({"task": …},
   {"chat": FakeSubagentChat(), ..., "subagent_timeout_seconds": 300.0})` sin `timeout`
   → funciona (test existente con context sin `subagent_timeout_seconds` sigue verde:
   kw-only con default 300.0).
9. **Override por LLM (monkeypatch de `subagent_module._run_one_subagent`):** `timeout=600`
   → recibe `timeout_seconds == 600.0`; `timeout=0` → recibe `timeout_seconds == 0.0`
   (sin timeout); `timeout=-1` → recibe el default configurado + nota en el resultado.

## Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Comando interactivo se cuelga para siempre (sin cap) | Esc cancela el run en vuelo (I-108); la descripción del parámetro instruye al modelo a hacer no-interactivos los comandos que piden input. Aceptado por el owner como trade-off de la libertad. |
| Modelo envía timeout pathológico (string / negativo / bool) | `sanitize_timeout` cubre todos los casos → fallback al default + nota visible en el resultado. |
| El LLM abusa del parámetro (p. ej. siempre 999999) | La descripción sugiere subirla solo para builds/tests/entrenamiento; el default 30 s sigue siendo el camino por defecto; observable en la traza. |
| Cambio de schema invalida prompt cache | Un solo cambio de properties por release; costo marginal (1 propiedad `number`). |
| Nota prepended contamina el tool result | Solo aparece con valor saneado (casos raros); es explícita y accionable. |
| Romper config/env existente del subagent | `subagent_timeout_seconds` queda en inject intacto; `timeout=None` → default de config. Tests de config (`test_config_unit.py`) y de subagent existentes (`test_subagent_fallback.py` con `subagent_timeout_seconds: 10.0` por context) no se tocan y deben seguir verdes. |
| `timeout=0` en bash (sin timeout) | Deliberadamente no soportado (`allow_zero=False`): el shell es el hang más probable; el subagent sí lo permite por semántica existente. |
| `_run_bash`/`_run_one_subagent` llamados con otros args | Firmas internas inalteradas → tests existentes no tocan nada. |
